# QQ Mail live observation — 2026-10-07

Scope: one owner-operated account on Windows via `spikes/imap-dialect-probe`
(strictly read-only: LOGIN, EXAMINE, UID SEARCH, LIST, LOGOUT), TLS to
imap.qq.com:993. Baseline mailbox: 33 messages. This record contains no
addresses, subjects, folder contents, message IDs, or authorization data —
the probe redacts the account to `<account>` before anything reaches stdout.

Purpose: settle the v0.4 search surface (`ServerSearchField`) and the drafts
folder resolution (`cleaner.DraftsFolder`) against the real server before
tagging 0.4.0.

## 1. `TEXT` is silently ignored — never ship it (confirmed live)

- `UID SEARCH TEXT "qqmailprobeabsentword"` (a word present in no message)
  returned **OK with all 33 UIDs** — the full mailbox.
- `UID SEARCH TEXT "qqmail"` also returned 33, indistinguishable from an
  ignored criterion.
- Interpretation: the server answers OK while discarding the `TEXT` key. This
  is the worst dialect shape: no error surfaces, and a keyword search would
  present the entire mailbox as hits. The planned runtime guard (BAD →
  `policy_denied`) can never trigger for `TEXT`.
- Product consequence: `ServerSearchField = "BODY"` (internal/imapx/client.go),
  and `meta.search_mode` reports `server_body`. The `TEXT` branch is kept in
  the switch only as dead documentation of the rejected alternative.

## 2. `BODY` genuinely filters (confirmed live)

- `UID SEARCH BODY "qqmail"` → 0 hits; `BODY "qqmailprobeabsentword"` → 0
  hits; had `BODY` been ignored both would have returned 33.
- Contract effect: `search --server` matches **message bodies only** — not
  subjects or senders. Subject/sender filtering stays on
  `envelope list --subject/--from` (documented in USER_GUIDE §10).

## 3. Header criteria and date windows work (confirmed live)

- `UID SEARCH TO <account>` → 32 of 33 (one message not addressed to the
  account): real filtering. The `envelope list --to` shipped in v0.4 rests on
  working server behavior.
- `UID SEARCH BEFORE 1-Feb-2026` → 0 (the mailbox holds no older mail —
  consistent, not an error); `UID SEARCH SINCE 1-Jan-2026` → 33;
  `UID SEARCH SINCE 1-Jan-2026 BEFORE 1-Feb-2026` → 0. Date criteria compose.
- `UID SEARCH SINCE 1-Jan-2020` → 33: the baseline window equals the mailbox.
- `UID SEARCH CC "x@y.z"` → 33 (silent ignore suspected — an address matching
  no message cannot match all of them). No CLI surface exposes `CC`; recorded
  here so nobody reaches for it later.
- Wire-format note: dates on the wire are `2-Jan-2006` (no leading zero), as
  go-imap emits them.

## 4. Drafts folder: plain `Drafts`, no special attribute (confirmed live)

- `LIST "" "*"` returned: `INBOX`, `Sent Messages`, `Drafts`,
  `Deleted Messages`, `Junk` — all plain ASCII except a `\NoSelect \HasChildren`
  parent `其他文件夹` (wire form `&UXZO1mWHTvZZOQ-`, decoded via
  `imapx.DecodeMailbox`).
- The drafts folder is named **`Drafts`** and carries **no `\Drafts`
  special-use attribute** — so `cleaner.DraftsFolder` resolves it through the
  candidate-name fallback (first candidate hits). Same shape as the trash
  folder (`Deleted Messages`, no `\Trash`), which is why `cleaner.TrashFolder`
  already uses candidates.
- `APPEND` to `Drafts` (the `--save-draft` path) targets this folder; the
  `\Draft` flag on the appended message is a flag, not a folder attribute, and
  is unaffected.

## Conclusions

1. `ServerSearchField = "BODY"` (constant in internal/imapx/client.go; the
   wire test `TestSearchMapsBodyCriterion` pins the emitted form).
2. `cleaner.DraftsFolder` candidate list `["Drafts", "草稿箱"]` stands as
   shipped; `Drafts` resolves first. No code change.
3. `envelope list --to` and the date windows rest on confirmed server
   behavior; `TEXT` and `CC` must not be surfaced as search criteria.
4. Environment caveat: one account, 33 messages, 2026-10-07. Re-probe if QQ's
   behavior is suspected to have moved; the probe lives at
   `spikes/imap-dialect-probe` and prints a redacted JSON document.
