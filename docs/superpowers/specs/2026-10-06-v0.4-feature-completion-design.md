## 0. 背景与目标

与腾讯官方 `agently-cli`（QQ Agent 邮箱）的功能面对比（2026-10-06 会话）确认了一批
qqmail-cli 在自身定位内（标准 IMAP/SMTP、安全优先、QQ 单服务商做透）完全可实现但尚未
实现的功能。本批次一次性补全，前提是不触碰项目任何既有安全承诺：

- 不新增永久删除路径，禁 EXPUNGE/CLOSE 的协议断言与 AST 守卫保持不变；
- 不做实时推送（watch 维持诚实轮询）；
- 不做网页版专属能力（通讯录、日历、超大附件中转站）；
- 不支持群发（单次调用单封、白名单、TTY 人工确认三个发送门禁全部保留）；
- 不支持多服务商。

### 自主决策记录（评审时可推翻）

## 4. F2 — envelope list 过滤器补全（Wave 1）

新增三个参数，全部叠加在既有 `SearchFilter` 语义之上：

- `--before <窗口>`：与 `--since` 同构的时间上界（`24h`、`7d` 或 `YYYY-MM-DD`），
  映射 IMAP `BEFORE` 准则。`--since` 与 `--before` 可并用形成区间。
- `--to <子串>`：收件人大小写不敏感子串匹配，映射 IMAP `TO` 头准则（与既有
  `--from`/`--subject` 同机制）。是否被 QQ 服务器正确支持以 Wave 0 探测为准；
  不支持时命令返回结构化 usage/policy 错误并指向 compat 文档，绝不静默忽略。
- `--has-attachments`：**先实化数据源，再客户端过滤**。现有 `FetchEnvelopes` 对
  `has_attachments` 硬编码 false（只抓 HEADER 无法判定，schema 亦明示 "always false
  in bulk listings"）——本项一并修复：FETCH 追加 `BODYSTRUCTURE`，按叶部件类型与
  disposition 推导真值（这同时消除既有 schema 缺陷），随后在取回的信封上过滤。语义
  明确为：先按 `--limit` 从服务器取回窗口，再过滤，本页命中数可以少于 `--limit`；
  `meta.truncated` 与翻页游标语义不变。文档与 `--help` 说明这一顺序，避免"过滤后凑满
  limit"的误期许（凑满需要额外往返，违背本项目的限流纪律）。

不改翻页机制（`--before-uid`）与现有过滤器。

## 5. F1 — 服务端关键词全文搜索（Wave 1）

命令形态：`qqmail-cli search <query> --server [flags]`。

- `--server` 与 `--local` 互斥，二者必须恰选其一。现有契约（"必须 `--local`"）由
  "必须二选一"替代——对既有调用者行为不变（只带 `--local` 的调用照旧工作）。
- 服务端映射：query → IMAP `TEXT` 准则（探测确认 QQ 支持时）；若 QQ 只支持 `BODY`
  则映射 `BODY` 并在输出 `meta` 中标注 `server_search_field`；若两者皆不可用，
  `--server` 返回结构化错误（`policy_denied` 语义族，指向 compat 文档），本地检索
  提示指向 `sync` + `--local`。
- 命中后走既有 `FetchEnvelopes` 管线返回信封列表，输出形状与 `envelope list` 同构
  （复用 `envelope.list` 的信封 schema，顶层 command 为 `search`）。
- `meta.search_mode` 取值扩展为 `server_text` / `server_body` / `local`。
- 限流纪律不变：单次调用单连接，一次 SEARCH 一次取回；`--limit` 复用既有
  1-500 约束，默认 50。
- 安全不变量：搜索词与命中内容都是不可信数据；query 不进日志（审计内容无关原则）。

## 6. F11 — 内嵌图片（CID 部件）入附件清单（Wave 1）

背景（2026-10-06 探针实证，探针已删，结论落档）：一封典型 `multipart/related`
邮件（`text/html` 引用 `cid:image001` + `Content-Disposition: inline` 的 PNG 部件）
在现有解析下——主解析器（go-message）的 `InlineHeader` 分支只处理 `text/plain` 与
`text/html`（`internal/mimeparse/parse.go:77-95`），其余 mediaType **静默跳过**，
导致：`attachment list` 为 0、`attachment download` 不可用（取证/留档硬伤）、
HTML 阅读档 `<img src="cid:...">` 被 bluemonday 白名单剥除、`forward` 只重挂
`parsed.Attachments`（为 0）而丢图。兜底解析器（enmime）反而会把带文件名的 inline
部件归入附件，但主解析器几乎不报错、兜底路径基本轮不到。

设计（改动集中在 `internal/mimeparse`，一处修复全链路受益）：

1. **inline 部件入附件清单**：`InlineHeader` 分支对既非 `text/plain` 又非 `text/html`
   的叶部件（典型 `image/*`，不限于）收入 `result.Attachments`：`Index` 沿用现有
   续排序号；`Filename` 走既有 `Filename()` 路径，为空时兜底 `inline-<index>`；
   `ContentID` 取 `Content-ID` 头（剥 `<>` 包裹）填入既有字段
   （`mailmodel.Attachment.ContentID` 已存在，主解析器从不填——本项开始有值）。
   multipart 叶部件由 go-message 的遍历递归处理，本分支天然只见叶部件，无递归问题。
2. **下游零改动受益**：`attachment list`/`attachment download` 立即可见可下（index/all
   机制、防穿越、不覆盖语义全不变）；`forward` 自动携带内嵌图（send.go 既有
   `parsed.Attachments` 重挂逻辑）；`content_id` 在 `attachment list` 输出中开始出现。
3. **has_attachments 口径**：信封侧的 `has_attachments` 由 F2 实化（BODYSTRUCTURE
   推导）。任务中核对解析口径与信封口径对 related 邮件的取值一致性；若服务器方言
   导致两者不一致，在 `docs/compat/` 记录差异，只记录，不改判定（字段语义不变原则）。
4. **HTML 阅读档维持剥 `<img>`（已决策）**：bluemonday 白名单不加 `img`——放行等于
   渲染远程图，带来跟踪像素隐私风险；用户要看图走 F11 的附件下载路径。`<script>` 剥除
   的既有安全收益不变。此为安全策略决策，默认维持剥除，如需放行另开 spec。
5. **测试**：合成 `multipart/related` 夹具（text/html 引用 cid + inline PNG 部件）回归
   全链路：解析计数与 content_id、attachment list/download、forward 携带、文本/HTML
   阅读档表现。仓库不收真实邮件样本，夹具全合成。

## 7. Wave 2 — 写动词四件

全部走既有 mutate 门禁管线（`message_mutate.go` 模式）：dry-run 默认输出动作与数量
→ `--execute` → `policy.RequireMutationAllowed` → 真实 TTY `confirmExactCount` →
逐封执行、失败进 `warnings[]` → 审计 JSONL。`QQMAIL_CLI_READONLY=1` 锁死全部四个命令
（守卫测试逐个断言）。

### F3 `message mark-unread <id>...`

`mark-read` 的镜像。新增 imapx 写原语 `StoreFlags(ctx, id, add, remove []string)`（或
等价签名），实现 `STORE +FLAGS/-FLAGS`。policy 层新增 `MarkUnread`，与 `MarkRead`
同一批门禁与审计路径。read 面不受影响（读路径仍 EXAMINE+PEEK，不消费 \Seen）。

### F4 `message flag <id>... --add \Flagged | --remove \Flagged`

星标管理。`--add` 与 `--remove` 互斥且必选其一；旗标值 v0.4 只接受 `\Flagged`
（即 QQ 网页端的"星标"），其他值一律 usage error——扩展面留给未来，不在本批开放。
底层复用 F3 的 `StoreFlags` 原语。安全说明写入文档：**加星是保护动作**（`triage plan`
对星标邮件绝对排除），**去星是降低保护**，两者都要求人工 TTY 确认，去星的 dry-run
输出中明确提示该邮件将失去清理排除保护。`clean`/`restore` 的星标排除逻辑不改动——
排除判定基于执行时刻的服务器旗标状态，天然感知本命令的结果。

### F5 `message trash <id>...`

单封/批量移入服务器回收站的直达命令，是 `message move` 的特化：

- 目标文件夹由既有 `cleaner.TrashFolder(ctx, reader)` 解析（`\Trash` 属性优先，
  候选名兜底），解析失败即命令失败，绝不猜测文件夹名。
- 复用 move 的完整管线：文件夹一致性检查、`MoveUID` / 无 MOVE 能力时的
  `CopyMarkDeletedUID` 保底路径、目的地确认、审计。
- 新增一条前置检查：id 内嵌文件夹已是回收站时返回 usage error（与 agently-cli 的
  `+trash` 边界一致，避免无意义往返）。
- 服务端 30 天自动清除是 QQ 行为，CLI 不承诺、不提示倒计时；`restore --plan` 语义
  不变（本命令不经 plan，误删单封的找回路径是 `message move` 反向操作或备份导出）。

### F9 `folder create <name>` / `folder rename <old> <new>`

- 新增 imapx 写原语 `CreateFolder(ctx, name)`、`RenameFolder(ctx, old, new)`，实现
  `CREATE`/`RENAME`，名称经既有 Modified UTF-7 编码路径处理中文。
- `folder rename INBOX <任何名字>` 返回 usage error（IMAP 对 RENAME INBOX 有移动全部
  邮件的特殊语义，禁用）。`folder create INBOX` 同理拒绝。
- **不做 `folder delete`**：删除文件夹连带删除其中邮件，与"不可删"承诺冲突的边界
  不开；文档明示。
- dry-run 展示将创建/重命名的名称（人读输出过 `output.SanitizeHuman`）。

## 8. Wave 3 — 发送面四项

### F6 `reply --reply-all`

基于审计轮后的语义（收件人 = 原邮件 Reply-To，缺省 From；`--to` 被拒绝）：

- `--reply-all` 时收件人集合扩展为：To = Reply-To/From ∪（原邮件 To − 本账号地址）；
  Cc =（原邮件 Cc − 本账号地址 − 已在 To 中的地址）。地址比较大小写不敏感，去重后
  按原邮件出现顺序排列。
- **原邮件 Bcc 永不传播**（Bcc 本就不出现在收到的信封里，此条为防御性断言，写入测试）。
- `--cc`/`--bcc` 追加语义不变，可与 `--reply-all` 并用。
- dry-run 预览必须完整展示扩展后的 to/cc/bcc（这是 send 门禁的确认面，扩展收件人
  是本次变更的风险核心，预览不得省略）。
- 收件人总数仍受既有 10 人上限约束，超限 usage error。

### F8 `--body-format html`（send/reply/forward）

- `--body-format text|html`，默认 `text`，对 `--body` 与 `--body-file` 同时生效；
  1 MiB 正文上限按格式化后源码字节计，不变。
- MIME 构建（`internal/sendmail/message.go`）：`Draft` 增加 `BodyHTML string` 与
  `BodyFormat` 字段。`html` 时 CLI 确定性地生成纯文本降级（剥离标签、解码实体、
  折叠空白），产出 `multipart/alternative(text; html)`；有附件时 alternative 嵌套在
  既有 `multipart/mixed` 内。纯文本发送路径字节级不变（回归测试锁定）。
- **CLI 不消毒 HTML**：用户的 HTML 原样发送（与"不 reinterpret 用户内容"的项目原则
  一致；消毒既改变内容也制造虚假安全感）。收信端安全由既有读路径的不可信处理承担。
- **dry-run 预览展示**（本特性的安全设计核心）：
  1. 降级后的纯文本（人类确认的就是收件人在纯文本视图看到的降级内容）；
  2. HTML 源码摘要：转义控制符/ANSI/bidi 后截断（默认前 2 KiB）展示，标注总字节数；
  3. 固定警示行：`HTML 正文将原样发送，未经消毒；请检查上方源码摘要`。
- TTY 确认字样（`SEND`）与三门禁不变。人读预览全程过既有脱敏管线（`output` 包），
  untrusted paths 测试扩展到 HTML 摘要字段。

### F7 `--save-draft`（send/reply/forward）

- `--save-draft` 将命令的完成动作从 SMTP 提交替换为 IMAP `APPEND` 到草稿箱：
  同一 `Draft` 构建路径（含附件、含 F8 的 HTML alternative、reply/forward 的线程头），
  落点不同。APPEND 携带 `\Draft` 旗标。
- 草稿箱解析走 Wave 0 探测结论：`\Drafts` 特殊属性优先，候选名兜底
  （`Drafts`、`草稿箱` 等，以探测实测为准），解析失败即失败，不猜测。
- **风险级别 = mutate 而非 send**：存草稿不发送，不触发 send allowlist 语义
  （allowlist 管"发出去给谁"，不管"存了什么"）；但仍是服务器写，走 dry-run 默认 +
  `--execute` + TTY 数量确认 + 审计 + readonly 锁死。`agent-info` 标注 mutate。
- 交互组合：`--save-draft` 可与 `--execute` 并用（存草稿）；与发送互斥——同一次调用
  要么发送要么存草稿，不存在既发又存（QQ SMTP 侧已有 Sent 副本，无需 CLI 重复落）。
  dry-run 输出明确标注完成动作是 `save_draft` 还是 `send`。
- 附件与正文上限同发送路径（20 MiB 合计 / 1 MiB 正文）。

### F12 `--attach-inline` 内嵌图发送（send/reply/forward）

发送侧探针审计确认：`Draft` 无 HTML 字段、`Build` 只产 `text/plain` + `multipart/mixed`，
没有 `multipart/related`、没有 Content-ID 生成；所有既有门禁与此缺口无关，纯功能缺失。
F8（`--body-format html`）补上 alternative，本项补上 related：

- `--attach-inline <path>`（可重复，三命令同构）：**要求 `--body-format html`**——
  `cid:` 引用只成立于 HTML 正文，无 HTML 正文时 usage error。
- MIME 结构：有 inline 附件时 `Build` 产出 `multipart/related`——root 为 F8 的
  `multipart/alternative`（text + html），随后每个 inline 部件带 `Content-ID`、
  `Content-Disposition: inline; filename=...`、嗅探的 Content-Type（缺省
  `application/octet-stream`）。
- Content-ID 生成：`<crypto/rand hex@qqmail-cli.local>`，同一次调用内唯一；用户在
  HTML 正文里以 `<img src="cid:...">` 引用（文档给示例，CLI 不改写用户 HTML）。
- 注入校验：文件名与 Content-ID 头值走既有头部注入防御（CRLF/控制符），扩展
  `validateDraft`。
- 上限：`--attach-inline` 与 `--attach` 合计进既有 20 MiB 上限；数量上限同附件路径。
- 预览：dry-run 与 TTY 确认前列出全部 inline 部件（文件名、类型、字节、Content-ID）；
  白名单/TTY/单封三门禁零变化。

## 10. 安全模型增量汇总

| 层 | 增量 | 验证方式 |
|---|---|---|
| 写边界 | `StoreFlags`/`AppendDraft`/`CreateFolder`/`RenameFolder` 四个新原语全部落在 `internal/imapx/mutate.go` 单文件，仅 policy 层可调 | go/ast 静态扫描白名单更新（CI） |
| 只读 | reader 方法面零变化 | 既有反射白名单测试不动且必须保持绿 |
| 协议 | 仍无任何 EXPUNGE/CLOSE 下发路径 | 既有协议线路断言扩展覆盖新原语（新原语的线路只允许 STORE/APPEND/CREATE/RENAME） |
| readonly | 全部新写命令被 `QQMAIL_CLI_READONLY=1` 锁死 | 逐命令守卫测试（未知取值按只读的既有语义不变） |
| 审计 | 四类新写动作全部进内容无关审计 JSONL | 既有审计测试模式扩展 |
| 不可信面 | HTML 源码摘要、内嵌图文件名与 Content-ID、文件夹名、扩展收件人列表进入人读输出 | untrusted paths 测试扩展 + 脱敏管线复用 |
| 解析边界 | inline 非文本部件不再静默丢弃，入附件清单（F11）——只影响读取面输出，不新增任何写路径 | 合成 multipart/related 夹具回归 |
| 发送门禁 | 白名单/TTY/单封三门槛零放松；HTML 与内嵌图都不改变确认字样与流程 | 既有 send 门禁回归 + 新预览字段断言 |
